# 06 日常運用とログ

- 下書き: アカウントを選び、500換算以内で保存。普通のかな・漢字は1コードポイントを1、絵文字のクラスタはUTF-8バイト長で数えます（😀=4、家族のZWJ連結👨‍👩‍👧‍👦=25）。結合文字や表示環境で見た目の文字数と異なります。下書き保存だけでは公開しません。
- 連投: 「連投を作成」を選び、改行した `---` で2〜10件に分割。先頭からまとめて予約・取消・非表示します。
- 予約: 保存後に日時を指定し「予約する」。画面の日時は端末のローカル時刻です。空欄で「公開する」を押すと順次送信します。
- 取消: 処理前の公開待ちのみ。処理開始後は取り消せません。
- 非表示: 下書き・公開済みを一覧から隠します。Threads上の投稿削除ではありません。
- インサイト: 公開済みの記事で views / likes / replies / reposts / quotes / shares の6指標を取得。sharesはMeta側で開発中の指標です。未取得の数値は0にせず「未取得」と表示します。

`failed` は作成段階の明確な拒否、コンテナのERROR/EXPIREDなど、公開前の停止状態です。トークン失効だけで未処理の予約をfailedへ消費しません。原因を直してから新しい下書きで準備します。

`needs_review` は成否不明または処理が停止した状態です。診断コードとThreads上の公開結果を確認してください。後続連投も停止し、自動再送しません。新規の原稿として再投稿する前に、重複の有無を必ず確認します。

新しい予約はアカウントごとのDOが処理し、既存予約は従来のtenant DOが処理します。空のキューではDOアラームを停止します。未来の予約はその時刻まで待機し、新規投入で再起動します。処理中のジョブは状態確認・障害復旧用の起動を残します。

## Metaの公開上限と予約

プロフィールごとにローリング24時間でAPI投稿250件、返信1,000件です。連投の先頭は投稿枠、2件目以降は返信枠を使います。現在の枠は「投稿枠を確認」、APIでは `GET /{user-id}/threads_publishing_limit` で確認できます。返信枠取得には `threads_manage_replies` も必要です。

即時公開の予約では現在の残枠と、この環境で近い期間に予約済みの件数を確認し、不足なら下書きのまま拒否します。将来日時では現在の残枠がそのまま有効とは限らないため警告を表示します。実行時に再確認して不足が分かった場合は、状態を消費せず5分後に確認します。他アプリの投稿やMeta側の計測遅延もあるため、事前確認が実際の公開を保証するわけではありません。公開POSTの結果が不明ならneeds_reviewを維持します。

一般のAPI呼び出し上限は投稿枠とは別です。公式式はアプリとユーザーの組合せごとに `4,800 × 過去24時間のインプレッション数`、最小10インプレッションとして計算します（最小48,000回/ローリング24時間。「毎時」ではありません）。

## コンテナの確認

テキストの状態確認は1分間隔・最大5回、画像・動画は最大15回です。カルーセルの子素材も各15回で停止します。状態取得GETの404やIN_PROGRESSは同じコンテナを保持して再確認します。ERRORとEXPIREDは理由を分け、PUBLISHEDは重複を防ぐため照合待ちにします。保存・表示するerror_messageは公式の固定列挙だけで、任意の上流文面は残しません。

publishのcode 24 / subcode 4279009について、「絶対に未実行」とする保証は確認できていません。公開POSTを自動再送する根拠には使いません。

## リンクと未対応機能

投稿内のユニークなリンクは5つまでです。2025-12-22以降、超過すると作成段階で拒否されます。同じURLの重複は1つとして扱われます。自動のURL数判定は実装していないので、投稿前に確認してください。

Threads APIには投稿削除・アカウントのフォロワー属性取得もありますが、この製品の「非表示」は削除APIを呼びません。フォロワー属性も現在の投稿インサイトには含めません。API版は公式例と同じv1.0です。廃止日を推測せず[Changelog](https://developers.facebook.com/documentation/threads/changelog.md)を確認します。

仕様: [投稿・絵文字・リンク](https://developers.facebook.com/documentation/threads/posts.md)、[クォータ](https://developers.facebook.com/documentation/threads/overview.md)、[コンテナ状態](https://developers.facebook.com/documentation/threads/troubleshooting.md)、[インサイト](https://developers.facebook.com/documentation/threads/insights.md)。

## ログと保持

`observability.enabled=true` でWorkers Logsを有効にします。認証URLの保存を避けるためinvocation logsは無効にし、明示的な診断イベントだけを記録します。コード・例外全文・トークン・リクエストURL・上流レスポンス本文をログに追加しないでください。

保存日数と上限は[Cloudflare Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)の契約プランに従い、配備先で確認します。この設定だけで無期限保存にはなりません。長期保管が必要なら、秘密除去済みの障害記録だけをアクセス制限した場所へ保存し、運営者が保持期限を決めます。D1の下書き・会話に関する所有データ・投稿履歴は自動削除しません。

WFPでは配備側もobservability設定を反映する必要があります。バンドルを生成しただけで既存テナントのログ設定は変わりません。

## 画像・動画・カルーセル（v0.1.3）

1. 「投稿形式」で画像1枚／動画1本／カルーセルを選びます。
2. ログイン不要の公開HTTPS URLを入力します。共有ページではなく、Metaから素材自体を取得できるURLが必要です。Harnessはファイルアップロード・代理ダウンロード・自動変換を行いません。
3. カルーセルは画像と動画を混在させて2〜20件。「前へ」「後へ」で順序を確認します。本文は省略できます（入力する場合は500換算以内）。
4. 下書き保存後、本文・素材リンク・順序・投稿先・予約日時を確認して公開します。URLの確認リンクは別タブで開きます。自動プレビューは行いません。
5. MetaがURLから素材を取得し、全素材の処理が完了してから公開します。予約時点では素材取得や形式の検査はしません。公開完了までURL・内容・アクセス権を維持してください。期限の短い署名付きURLは予約に不向きです。

画像: JPEG/PNG、8MB以下、sRGB、比率上限10:1、幅320〜1440（範囲外はMetaが調整）。動画: MOV/MP4、HEVC/H.264、23〜60fps、最大幅1920、比率0.01:1〜10:1、0秒超〜300秒、1GB以下。音声はAAC・48kHz以下・1/2ch。詳細は[Meta公式の素材仕様](https://developers.facebook.com/documentation/threads/posts.md)を確認してください。URLの形式のみ保存時に検証し、ファイル形式・サイズ・コーデックの最終判定はMetaに委ねます。

カルーセル全体で投稿枠1件です。子素材は単独公開せず、作成済みIDと準備状態を保存して別tickで続きを処理します。素材作成や公開結果が不明な場合は再作成・再公開せず確認待ちになります。素材ERROR/EXPIREDは公開前停止、状態確認のタイムアウトは確認待ちです。

API/MCPでは `media: [{"type":"IMAGE","url":"https://cdn.example.com/a.png"},{"type":"VIDEO","url":"https://cdn.example.com/a.mp4"}]` を下書きに指定します。1件なら単体投稿、2〜20件ならカルーセルです。連投APIのpartsは従来の文字列に加え `{text, media}` を受け付けます。画面でメディア付き連投を作る場合は、まずテキスト連投の下書きを保存し、各原稿の編集で素材を追加してから先頭の公開操作を行います。

実Metaで確認済みなのはテキスト単発と6指標取得です。メディアの実投稿確認は、素材・本文・投稿先の承認後に行います。模擬Metaでの自動テストと実Meta公開を混同しないでください。
